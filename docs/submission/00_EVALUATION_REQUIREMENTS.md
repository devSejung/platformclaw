# 공식 제출·심사 요구사항 — 익명 요약

이 문서는 제공된 공식 안내 메일의 읽기용 본문을 개인 식별정보 없이 요약한다. 원문 파일, sender/recipient, 이름, 이메일, 전화번호, 부서, Message-ID, tracking markup은 저장소에 복사하지 않았다. 의미·비중·anchor는 변경하지 않았다.

## 필수 제출물과 형식

| 제출물          | 형식·제한                                        | 필수 |
| --------------- | ------------------------------------------------ | ---- |
| 코드 저장소     | GitHub URL, 심사 접근 권한                       | 예   |
| 프로젝트 소개서 | HTML 슬라이드                                    | 예   |
| 데모 영상       | MP4, 5분 이내                                    | 예   |
| 프로젝트 문서   | 저장소 안의 Markdown, README·PRD·ARCHITECTURE 등 | 예   |

평가는 commit history나 log보다 제출 시점의 마지막 commit에 있는 최종본을 기준으로 한다. 개발 과정, 시행착오와 논의는 Markdown 문서에 가능한 한 남겨야 한다. 영상은 실시간 녹화가 필수는 아니며 screenshot 중심 scenario도 허용된다. 보안상 actual data 사용이 어렵다면 dummy data를 사용할 수 있다. Markdown 문서는 AI 심사의 직접 근거로 사용된다.

Open source를 사용하거나 기존 프로젝트를 확장하거나 대규모 시스템의 하위 버전인 경우, 해커톤 범위와 출처를 README에 명시해야 한다.

## 선발 방식

- 본선: 전 참가팀을 독립 AI 평가가 블라인드로 전수 채점해 20팀을 선정한다.
- 결선: 본선 20팀의 AI 점수 70%와 구성원 투표 30%를 합쳐 5팀을 선정한다.
- 본선 제출물의 영상과 소개서는 online campus에 전시될 수 있다.

## 평가 항목과 비중

| 항목          | 비중 | 평가 초점                    |
| ------------- | ---: | ---------------------------- |
| 기술성        |  30% | 코드 품질, 설계, 기술 난이도 |
| 창의성        |  25% | 차별성, 접근의 새로움        |
| 완성도        |  20% | 실제 동작, 안정성, UX        |
| 비즈니스 가치 |  15% | 사내 적용성, 파급 효과       |
| 전달력        |  10% | 전달 명확성, storytelling    |

각 항목은 서로 다른 AI Agent가 독립된 context에서 평가한다. 한 항목의 문서 표현이 다른 항목 점수를 대신하지 않는다. 핵심은 실제 동작 결과와 문서·코드·evidence의 정합성이다.

## 1·3·5점 Anchor

2점과 4점은 인접 anchor의 중간 수준이다.

| 항목              | 1점                                            | 3점                                                 | 5점                                             |
| ----------------- | ---------------------------------------------- | --------------------------------------------------- | ----------------------------------------------- |
| 기술성 30%        | 동작 불안정, 구조 없는 짜깁기, 핵심 logic 미완 | 동작하며 표준 구조·library를 사용하고 난이도가 평이 | 견고한 설계·예외 처리, 비자명한 기술 난제 해결  |
| 창의성 25%        | 기존 solution 단순 재현, 차별점 없음           | 익숙한 접근을 부분 변형·조합                        | 문제 정의와 접근이 새롭고 기존 대비 명확히 차별 |
| 완성도 20%        | demo 다수 실패, 핵심 기능 미구현·미동작        | 주요 기능 동작, 일부 bug 또는 거친 UX               | 전체 기능 안정 동작, 매끄러운 UI/UX             |
| 비즈니스 가치 15% | 적용처 불명확, 실용성 낮음                     | 사내 적용 여지가 있으나 파급 제한                   | 명확한 사내 적용처·파급, 즉시 활용 가능         |
| 전달력 10%        | 전달이 산만하고 핵심 파악 어려움               | 핵심은 전달되나 흐름·근거가 다소 약함               | 명확한 story와 근거로 설득력이 높음             |

## 점수와 재검증

항목별 1~5점을 비중으로 가중 합산한다. 동일 제출물을 반복 채점했을 때 점수가 크게 흔들리면 자동 재검증하고, 순위 경계의 팀은 pair 비교한다. 모든 점수와 평가는 인용 근거와 함께 기록해야 하며, 근거 없는 점수는 폐기 후 재평가한다. 수상권·경계선은 사람의 최종 검토 대상이다.

## 블라인드와 공정성

- 팀명, 사번, 부서 등 과제 외 신원 정보는 가리고 평가한다.
- 제출물에는 개인 이름, 연락처, 내부 hostname, secret을 넣지 않는다.
- 평가는 저장소의 code, test, runtime evidence와 문서 인용을 연결해야 한다.

## Prompt Injection 금지

코드나 문서에 점수를 요구하거나 평가 Agent를 조종·공격하는 숨은 지시문을 넣지 않는다. 이러한 내용은 탐지·제거되고 사람 검토 대상으로 flag되며 정식 과제로 선정되지 않을 수 있다. 이 저장소의 문서는 제품 사실과 검증 방법만 설명한다.
